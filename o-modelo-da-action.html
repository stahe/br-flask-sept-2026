    3. O modelo da action

    Uma action precisa das informações enviadas pelo navegador: os parâmetros da URL ([?name=martin&age=42]), os campos de formulário, o corpo JSON da requisição e, às vezes, um cabeçalho de requisição HTTP. O curso original chama todas essas informações de modelo da action. Este capítulo mostra como uma action recupera essas informações, as converte no tipo correto e as valida. Esse processo se chama binding de dados.

    O [Flask] é aqui muito mais minimalista que outros frameworks: ele dá acesso às informações da requisição na forma de strings e para por aí. Converter ["42"] no inteiro 42, verificar se um nome tem pelo menos dois caracteres, montar os campos em um objeto: tudo isso fica a cargo da aplicação. Faremos isso primeiro à mão (Exemplo 07) e depois com a biblioteca [Pydantic] (Exemplos 08 a 12), que descreve um modelo por meio de uma classe na qual cada campo declara seu tipo e suas restrições. No próximo capítulo, os formulários HTML serão tratados por outra biblioteca, [WTForms], concebida especificamente para eles; o [Pydantic] continua sendo a ferramenta natural para os parâmetros de uma URL e para os corpos JSON da API.

    Observação sobre a terminologia: no capítulo seguinte, a palavra “modelo” designará principalmente os dados que uma action transmite à sua view. O modelo de uma action, no sentido usado neste capítulo, é o que ela recebe.

    Os Exemplos 07 a 12 são executados da mesma forma que os do capítulo anterior: abra um terminal na pasta do exemplo, com o ambiente virtual ativado ([python app.py]); [Ctrl-C] interrompe o servidor. Seus arquivos [app.py] são todos parecidos: uma factory [create_app] que cria a aplicação, configura o provedor JSON (acentos preservados, chaves na ordem original; veja o Exemplo 03) e registra um blueprint. Só os comentaremos quando trouxerem algo novo.

    # controllers/parameters.py: os parâmetros da URL (a "query string")
from flask import Blueprint, abort, request

parameters = Blueprint("parameters", __name__, url_prefix="/parameters")


# /parameters/action01?name=martin: request.args contém os parâmetros da
# URL; get retorna o valor do parâmetro, ou None se ele estiver ausente
@parameters.get("/action01")
def action01():
    name = request.args.get("name")
    return f"name = [{name}], of type {type(name).__name__}"


# /parameters/action02?age=42: type=int CONVERTE o valor (uma string) em
# inteiro; um parâmetro ausente, ou que não seja um inteiro, resulta em None
@parameters.get("/action02")
def action02():
    age = request.args.get("age", type=int)
    return f"age = [{age}], of type {type(age).__name__}"


# /parameters/action03?age=42: um parâmetro OBRIGATÓRIO; sua ausência, ou um
# valor que não seja um inteiro, interrompe a ação com uma resposta 400 (Bad Request)
@parameters.get("/action03")
def action03():
    text = request.args.get("age")
    if text is None:
        # abort lança uma exceção, que o Flask transforma em uma resposta de erro
        abort(400, "the [age] parameter is required")
    # a conversão fica por nossa conta
    try:
        age = int(text)
    except ValueError:
        abort(400, f"[{text}] is not an integer")
    return f"age = [{age}], of type {type(age).__name__}"


# /parameters/action04?page=2: um valor padrão se o parâmetro estiver ausente
@parameters.get("/action04")
def action04():
    page = request.args.get("page", default=1, type=int)
    return f"page = [{page}]"


# /parameters/action05?q=flask: o nome do parâmetro da URL não é necessariamente
# o da variável Python
@parameters.get("/action05")
def action05():
    search = request.args.get("q")
    return f"search = [{search}]"


# /parameters/action06?name=martin&age=42: todos os parâmetros de uma vez, como um dicionário
@parameters.get("/action06")
def action06():
    return request.args.to_dict()
    • linha 11: [request.args] contém os parâmetros da URL, já decodificados pelo [Werkzeug]. É um dicionárioespecial, um [MultiDict], que, como veremos no Exemplo 10, aceita vários valores por chave. Seu método [get] devolve o valor de um parâmetro, ou [None] se ele estiver ausente. Ao contrário de [request.args["name"]], que lançaria uma exceção para um parâmetro ausente, [get] nunca causa erro;
    • linha 12: a action exibe o valor e seu tipo: [type(x)] é a classe de [x], e [__name__] é o nome dessa classe. Um valor recuperado da URL é sempre uma string ([str]);
    • linha 19: o parâmetro [type] de [get] especifica uma função de conversão aplicada à string: neste caso, [int], a classe dos inteiros, cuja chamada [int("42")] devolve 42. Se a conversão falha ([int("abc")] lança uma [ValueError]), [get] devolve [None], exatamente como para um parâmetro ausente: a action não consegue distinguir os dois casos, e o erro de entrada passa despercebido;
    • Linhas 26–35: um parâmetro obrigatório e uma conversão manual que distingue os dois erros possíveis. [abort(400, message)] encerra a action com uma resposta 400 (*Bad Request* — a requisição é inválida), acompanhada da mensagem (veja o Exemplo 03). A instrução [try] / [except ValueError] captura a exceção lançada por [int];
    • linha 42: um valor padrão, usado se o parâmetro estiver ausente (ou se sua conversão falhar). É um caso típico para o número de página de uma lista;
    • linha 50: não há obrigação de dar à variável [Python] o mesmo nome do parâmetro da URL. Os mecanismos de busca costumam usar um parâmetro curto, [q] (*query*);
    • linha 57: [to_dict()] converte o [MultiDict] em um dicionário [Python] padrão (mantendo apenas o primeiro valor de cada parâmetro), que a action retorna: [Flask] o transforma em JSON (veja o Exemplo 03).

    Este primeiro exemplo ilustra os limites da abordagem manual: para cada parâmetro, é preciso escrever a leitura, a conversão e o tratamento dos valores ausentes e dos erros.     3.2. Exemplo 08: um modelo de action descrito por uma classe

    [Pydantic] é a biblioteca de validação de dados mais usada em [Python] (está no núcleo do framework [FastAPI]). Ela descreve os dados esperados por meio de uma classe: cada atributo tem um tipo e, opcionalmente, restrições. [Pydantic] encarrega-se de converter os dados recebidos nesses tipos e de validar as restrições. Ela está instalada no ambiente virtual do exemplo (arquivo [requirements.txt]).

    # models/person.py: o modelo da ação, uma classe Pydantic na qual cada
# campo carrega seu tipo e suas restrições
from typing import Annotated, Literal

from pydantic import BaseModel, ConfigDict, EmailStr, Field


class PersonModel(BaseModel):
    # as strings recebidas têm os espaços ao redor removidos
    model_config = ConfigDict(str_strip_whitespace=True)

    # obrigatório (sem valor padrão), de 2 a 20 caracteres
    name: Annotated[str, Field(min_length=2, max_length=20)]
    # um inteiro ("42" é convertido em 42), entre 0 e 150
    age: Annotated[int, Field(ge=0, le=150)]
    # somente um destes três valores
    title: Literal["Mr", "Mme", "Melle"]
    # opcional (None por padrão); se presente, um endereço de e-mail válido
    email: EmailStr | None = None
    • Linha 8: um modelo [Pydantic] é uma classe que herda de [BaseModel]. Seus atributos são declarados no nível da classe, junto com seus tipos, como em uma [dataclass] (Exemplo 06);
    • Linha 10: a configuração do modelo. [str_strip_whitespace=True] remove os espaços ao redor das strings recebidas: um nome digitado como [" martin "] passa a ser ["martin"] antes de ser validado. O atributo [model_config] não é um campo do modelo: [Pydantic] reconhece esse nome reservado;
    • Linha 13: o campo [name]. [Annotated[str, Field(...)]] lê-se “o tipo [str], anotado por [Field(...)]”. [Annotated], do módulo padrão [typing], permite anexar informações adicionais a um tipo — informações que [Python] ignora, mas que as bibliotecas leem: aqui, as restrições de [Pydantic], um comprimento de 2 a 20 caracteres ([min_length], [max_length]). O campo não tem valor padrão: ele é obrigatório;
    • linha 15: o tipo [int]: [Pydantic] converte a string ["42"] no inteiro 42 e rejeita ["abc"]. As restrições [ge] (*greater or equal*) e [le] (*less or equal*) limitam o valor. Também existem [gt] e [lt] para desigualdades estritas;
    • linha 17: [Literal["Mr", "Mme", "Melle"]] é o tipo dos três valores listados, e apenas desses;
    • linha 19: [EmailStr] é o tipo de um endereço de e-mail; [Pydantic] valida sua sintaxe com a biblioteca [email-validator] (que também é instalada por [requirements.txt]). [EmailStr | None]: um endereço ou [None]. O valor padrão [= None] torna o campo opcional.

    Este modelo descreve os dados esperados; ele não contém nenhuma instrução de validação. Isso é chamado de estilo declarativo.

    # controllers/persons.py: uma ação cujo modelo é uma classe Pydantic
from flask import Blueprint, request

from models.person import PersonModel

persons = Blueprint("persons", __name__, url_prefix="/persons")


# /persons/action01?name=martin&age=42&title=Mr
# model_validate: o Pydantic cria o objeto a partir do dicionário de parâmetros
# (BINDING: conversão das strings para o tipo de cada campo), depois verifica
# as restrições (VALIDAÇÃO). Um modelo inválido lança uma ValidationError,
# transformada em uma resposta 400 pelo app.py: a ação para por aí
@persons.get("/action01")
def action01():
    person = PersonModel.model_validate(request.args.to_dict())
    return {
        # model_dump: o objeto como dicionário (serializável em JSON)
        "person": person.model_dump(),
        "ageType": type(person.age).__name__,
    }
    • Linha 16: o método de classe [model_validate] cria um objeto [PersonModel] a partir de um dicionário — neste caso, o que contém os parâmetros da URL. Ele executa duas operações, nesta ordem: - binding: cada valor do dicionário é atribuído ao campo de mesmo nome, depois de ser convertido para o tipo do campo (["42"] → 42); - validação: as restrições de cada campo são verificadas (comprimento, limites, valores permitidos etc.).
    • Se uma das duas etapas falhar, [model_validate] lança uma exceção [ValidationError], que contém uma lista de todos os erros (não apenas o primeiro). A action não a trata: ela é interrompida; veremos quem cuida disso;
    • linha 19: [model_dump()] retorna o objeto como um dicionário, que o [Flask] pode converter em JSON;
    • linha 20: o tipo da idade, para mostrar que a conversão ocorreu.

    # app.py: a aplicação do exemplo 08
from flask import Flask
from pydantic import ValidationError

from controllers.persons import persons


def create_app():
    app = Flask(__name__)
    # JSON: acentos mantidos, chaves em sua ordem original (veja o exemplo 03)
    app.json.ensure_ascii = False
    app.json.sort_keys = False
    app.register_blueprint(persons)

    # um modelo inválido: a exceção ValidationError do Pydantic se torna,
    # para a aplicação INTEIRA, uma resposta 400 que detalha os erros
    @app.errorhandler(ValidationError)
    def invalid_model(e: ValidationError):
        errors = [{"field": ".".join(str(x) for x in err["loc"]), "message": err["msg"]}
                  for err in e.errors()]
        return {"status": 400, "errors": errors}, 400

    return app


if __name__ == "__main__":
    create_app().run(port=5000, debug=True)
    • Linhas 17–21: o decorador [@app.errorhandler(ValidationError)] registra um tratador de exceções: quando uma action lança uma [ValidationError] (ou uma exceção de uma classe derivada), o [Flask] chama essa função, passando a exceção como parâmetro, e usa o valor retornado por ela como resposta. Declarado no nível da aplicação, o tratador vale para todas as suas actions: toda action que valida um modelo se beneficia dele, sem precisar escrever uma única linha de código de tratamento de erros;
    • Linha 19: [e.errors()] retorna a lista de erros. Cada erro é um dicionário; mantemos duas informações: [loc] (*location*), o campo afetado, na forma de uma tupla ([("name",)]; veja o Exemplo 10 para uma tupla mais longa), e [msg], a mensagem. A expressão [[... for err in e.errors()]] é uma compreensão de lista: ela constrói uma lista aplicando a expressão da esquerda a cada elemento;
    • linha 21: uma tupla [(body, code)] (veja o Exemplo 03): um dicionário, convertido em JSON, e o código 400.

    3.3. Exemplo 09: validação realizada pela action

    No Exemplo 08, um formulário inválido interrompe a action, e o tratador da aplicação responde. Isso é conveniente para uma API, cujos clientes são programas que esperam uma resposta de erro padronizada. No entanto, uma página web muitas vezes prefere reexibir o formulário com as mensagens de erro: nesse caso, a action deve decidir como tratar um modelo inválido. O modelo [models/person.py] é o do Exemplo 08.

    # models/messages.py: as mensagens dos erros de validação, em inglês.
# Cada erro do Pydantic é um dicionário: seu TIPO ("missing",
# "string_too_short"...), o campo envolvido (loc), uma mensagem em inglês (msg),
# e o contexto (ctx): os valores das restrições ({"min_length": 2}...)
MESSAGES = {
    "missing": "the field is required",
    "string_too_short": "{min_length} character(s) at least",
    "string_too_long": "{max_length} character(s) at most",
    "int_parsing": "an integer is expected",
    "greater_than_equal": "the value must be greater than or equal to {ge}",
    "less_than_equal": "the value must be less than or equal to {le}",
    "literal_error": "unknown value",
    "value_error": "invalid value",
    "too_short": "{min_length} item(s) at least",
}


# o nome do campo: loc é uma tupla, ("name",) ou ("color", 1) para o 2º
# item de uma lista
def field(error: dict) -> str:
    return ".".join(str(x) for x in error["loc"])


# nossa própria mensagem; um tipo de erro desconhecido mantém a mensagem do Pydantic
def message_en(error: dict) -> str:
    template = MESSAGES.get(error["type"])
    if template is None:
        return error["msg"]
    # format substitui {min_length}... pelos valores do contexto
    return template.format(**error.get("ctx", {}))
    • Linhas 5–14: cada erro do [Pydantic] tem um tipo e um identificador único (["missing"] para um campo ausente, ["string_too_short"] para uma string curta demais etc.), independente da mensagem em inglês. O dicionário [MESSAGES] associa uma mensagem própria a cada tipo. Algumas contêm marcadores como [{min_length}], [{ge}]...: a documentação do [Pydantic] fornece, para cada tipo de erro, os valores de seu contexto;
    • linhas 20–21: o nome do campo que causou o erro, extraído da tupla [loc]. [".".join(...)] reúne os elementos da tupla — convertidos em strings — separando-os por pontos;
    • linhas 25–30: nossa própria mensagem de erro. [MESSAGES.get(...)] retorna [None] para um tipo de erro que não está no dicionário; nesse caso, usa-se a mensagem em inglês do [Pydantic]. Caso contrário, [format] substitui cada ocorrência de [{name}] na mensagem pelo valor de mesmo nome do contexto: ["{min_length} character(s) at least".format(min_length=2)] produz ["2 character(s) at least"]. A notação [**dictionary] passa as entradas do dicionário como parâmetros nomeados; [error.get("ctx", {})] retorna um dicionário vazio para um erro sem contexto.

    Essa técnica (traduzir com base no tipo do erro) é a usada no estudo de caso: ali, as mensagens são identificadas por chaves, que são traduzidas para o idioma do usuário.

from datetime import date, datetime

from werkzeug.routing import BaseConverter, ValidationError


# um CONVERSOR do Werkzeug (a biblioteca na qual o Flask é construído):
# ele decide se um pedaço do caminho é adequado e o transforma em um objeto Python
class DateFrConverter(BaseConverter):
    # a expressão regular do pedaço do caminho: dd-mm-yyyy
    regex = r"\d{2}-\d{2}-\d{4}"

    # texto do caminho -> objeto date
    def to_python(self, value: str) -> date:
        try:
            # strptime verifica se a data existe: "31-02-2026" é rejeitada
            return datetime.strptime(value, "%d-%m-%Y").date()
        except ValueError:
            # a rota não corresponde: o Flask procura outra rota e, se não achar, responde 404
            raise ValidationError()

    # objeto date -> texto do caminho (usado por url_for)
    def to_url(self, value: date) -> str:
        return value.strftime("%d-%m-%Y")
    • linha 9: um conversor é uma classe que herda de [BaseConverter];
    • linha 11: o atributo [regex] é uma expressão regular que descreve o formato do segmento de caminho aceito: [\d] indica um dígito, [{2}] indica a repetição do elemento anterior — neste caso, dois dígitos. O prefixo [r] na string (*raw string*) impede que o [Python] interprete [\]. O roteamento só tenta usar esse conversor em um segmento de caminho com esse formato;
    • linhas 14–20: [to_python] transforma o texto do caminho em um objeto [Python], neste caso um [date]. [datetime.strptime] (*string parse time*) analisa uma string segundo um formato específico: [%d] para o dia, [%m] para o mês e [%Y] para o ano com quatro dígitos; [.date()] mantém a data sem a hora. [strptime] verifica se a data existe: [31-02-2026] tem o formato correto, mas lança uma [ValueError]. O conversor então lança a exceção [ValidationError] do [Werkzeug] (que não deve ser confundida com a do [Pydantic]): para o roteamento, a rota não corresponde à URL, o que resultará em um erro 404 se nenhuma outra rota corresponder a ela;
    • Linhas 23–24: a operação inversa, usada por [url_for] para construir uma URL a partir de uma data. [strftime] (*string format time*) formata uma data.

from functools import wraps

from flask import request


# @with_language, colocado em uma ação, passa a ela o parâmetro [language], lido do
# cabeçalho "Accept-Language: fr-FR,fr;q=0.9,en;q=0.8" -> "fr"
def with_language(action):
    # wraps: a função produzida mantém o nome da ação (o Flask o usa
    # para nomear a rota)
    @wraps(action)
    def action_with_language(*args, **kwargs):
        # request.accept_languages: o cabeçalho já analisado pelo Werkzeug;
        # best_match: o idioma preferido do navegador dentre os oferecidos
        kwargs["language"] = request.accept_languages.best_match(["fr", "en"], default="fr")
        return action(*args, **kwargs)

    return action_with_language
    • Linha 9: um decorador é uma função que recebe uma função (neste caso, a action) e retorna outra função (veja o Exemplo 01). Escrever [@with_language] acima de [def hello(...)] equivale a escrever, depois da definição, [hello = with_language(hello)];
    • Linha 13: a função que substituirá a action. [*args] recebe os parâmetros posicionais em uma tupla, e [**kwargs] (*keyword arguments*) recebe os parâmetros nomeados em um dicionário. É assim que o [Flask] passa as variáveis de caminho ([id=3]): a função as recebe sem precisar conhecê-las;
    • linha 16: é adicionado um parâmetro nomeado, [language]. [request.accept_languages] é o cabeçalho de requisição [Accept-Language], já analisado pelo [Werkzeug]. O navegador especifica aqui os idiomas do usuário, em ordem de preferência: [fr-FR,fr;q=0.9,en;q=0.8] (o coeficiente [q] mede a preferência, em uma escala de 0 a 1). [best_match] seleciona, entre os idiomas oferecidos pela aplicação, o que o usuário prefere, ou o valor [default] se nenhum for adequado;
    • linha 17: a chamada à action original, com os parâmetros recebidos e o novo. As notações [*args] e [**kwargs] desempacotam a tupla e o dicionário em parâmetros desta vez;
    • linha 12: a função [action_with_language] recupera o nome ([__name__]) e a documentação da action. Isso é essencial aqui: [Flask] dá a cada rota o nome de sua função (o [hello] de [url_for("examples.hello")]), e se recusaria a registrar duas rotas com o mesmo nome, [action_with_language], caso duas actions usassem o decorador.

    Veremos essa abordagem ao longo do curso: os decoradores [@login_required] e [@role_required] do capítulo sobre autenticação são construídos da mesma forma.

    # binding/types.py: tipos "caseiros" para os modelos Pydantic
from datetime import date, datetime
from typing import Annotated

from pydantic import AfterValidator, BeforeValidator


# uma restrição "caseira": a string não deve conter espaço.
# A função recebe o valor JÁ convertido para str; ela o retorna, ou lança
# um ValueError cuja mensagem se torna a do erro de validação
def no_space(value: str) -> str:
    if " " in value:
        raise ValueError("the field must not contain a space")
    return value


# Annotated: o tipo str, complementado por uma verificação executada DEPOIS da
# conversão. NoSpace é então usado como um tipo comum
NoSpace = Annotated[str, AfterValidator(no_space)]


# uma conversão "caseira": "23/09/2026" -> date(2026, 9, 23), executada ANTES da
# validação do tipo date
def date_fr(value):
    if isinstance(value, str):
        try:
            return datetime.strptime(value, "%d/%m/%Y").date()
        except ValueError:
            raise ValueError(f"[{value}] is not a valid dd/mm/yyyy date")
    return value


DateFr = Annotated[date, BeforeValidator(date_fr)]
    • Linhas 11–14: uma função de validação: ela recebe o valor do campo, retorna-o se for válido e, caso contrário, lança uma [ValueError]. A mensagem da exceção torna-se a mensagem do erro de validação;
    • linha 19: o tipo [NoSpace] é o tipo [str], anotado por [AfterValidator(no_space)]: o [Pydantic] chamará a função depois de verificar (e, se necessário, converter) o valor para [str]. Isso nos permite definir, uma única vez, um tipo que pode ser reutilizado em todos os modelos, como um tipo comum;
    • Linhas 24–30: uma função de conversão. O tipo ***[date] do *[Pydantic] aceita strings no formato internacional, ***[2026-09-23]; queremos o formato francês, ***[23/09/2026]. A função recebe o valor bruto : se for uma string, ela a converte em [date]. Qualquer outro valor (um [date]** já construído, por exemplo) é retornado como está;
    • linha 33: [BeforeValidator]: a função é chamada antes da validação do tipo [date], que, portanto, recebe um [date] já construído.

    # controllers/examples.py: binding e validação personalizados
from datetime import date

from flask import Blueprint, request, url_for
from pydantic import BaseModel, ValidationError

from binding.language import with_language
from binding.types import DateFr, NoSpace

examples = Blueprint("examples", __name__, url_prefix="/examples")


# /examples/schedule/23-09-2026: um conversor de caminho personalizado (veja app.py)
@examples.get("/schedule/<datefr:day>")
def schedule(day: date):
    # url_for usa o método to_url do conversor: date -> "23-09-2026"
    return f"schedule for the day [{day}], of type {type(day).__name__}, " \
           f"URL: {url_for('examples.schedule', day=day)}"


# /examples/hello: um parâmetro que não vem da URL, mas de um cabeçalho,
# fornecido pelo decorador @with_language
@examples.get("/hello")
@with_language
def hello(language: str):
    return "Hello!" if language == "en" else "Bonjour !"


# o modelo da busca: dois tipos "caseiros"
class SearchModel(BaseModel):
    keyword: NoSpace | None = None
    since: DateFr | None = None


# /examples/search?keyword=flask&since=01/09/2026
@examples.get("/search")
def search():
    model = SearchModel.model_validate(request.args.to_dict())
    return f"search for [{model.keyword}] since [{model.since}]"


# ——————————————————————————————— erros
# errorhandler de um BLUEPRINT: transforma uma exceção lançada por uma de SUAS
# ações em uma resposta (o mesmo decorador na aplicação vale para todas)
@examples.errorhandler(ValidationError)
def validation(e: ValidationError):
    # a mensagem do primeiro erro, sem o prefixo "Value error, " do Pydantic
    message = e.errors()[0]["msg"].removeprefix("Value error, ")
    return message, 400, {"Content-Type": "text/plain; charset=utf-8"}
    • Linhas 14–18: a variável de caminho [day] usa o conversor [datefr]: a action recebe um [date]. [url_for] constrói a URL dessa mesma action a partir da data, usando o método [to_url] do conversor. O separador [\] no fim da linha continua a instrução na linha seguinte; duas strings literais consecutivas são concatenadas;
    • Linhas 23–25: a ordem dos decoradores importa. Eles são aplicados de baixo para cima: [@with_language] primeiro transforma a action, depois [@examples.get] registra a função transformada no blueprint. Na ordem inversa, o blueprint registraria a action original, e o parâmetro [language] nunca seria fornecido;
    • linhas 30–32: um modelo que usa os dois tipos “personalizados” como se fossem tipos comuns. Os dois campos são opcionais;
    • linhas 45–49: um tratador de exceções, desta vez declarado no blueprint: ele trata apenas as exceções lançadas pelas actions desse blueprint. [removeprefix] remove o prefixo ["Value error, "] da mensagem, que o [Pydantic] acrescenta às mensagens de [ValueError]. A resposta é uma tupla de três elementos: o corpo, o código e um dicionário de cabeçalhos (veja o Exemplo 03), neste caso para uma resposta em texto simples.

    3.6.6. Conclusão

    Vamos resumir os métodos de que uma action dispõe para obter seu modelo:

    Origem
    Método
    Variáveis de caminho
    os parâmetros da action, tipados pelos conversores ([<int:id>], [<datefr:day>])
    Parâmetros da URL
    [request.args]: [get] (junto com [type] e [default]), [getlist], [to_dict]
    Campos de um formulário POST
    [request.form], um [MultiDict], e um [request.args]
    Corpo JSON
    [request.get_json()]
    Cabeçalhos
    [request.headers], e objetos já analisados, como [request.accept_languages]
    Conversão e validação
    um modelo [Pydantic]: [model_validate], [ValidationError], [e.errors()]
    Erros comuns
    [@app.errorhandler] (aplicação inteira) ou [@blueprint.errorhandler] (um blueprint)
    Parâmetro calculado
    Um decorador que adiciona um parâmetro nomeado à action

    Os formulários HTML, por outro lado, exigem mais do que simples validação: eles precisam ser exibidos, reexibidos com os dados digitados pelo usuário e os eventuais erros, e protegidos contra requisições forjadas. Esse será o papel do [WTForms], abordado no próximo capítulo, depois que as views forem apresentadas.

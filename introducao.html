    1.1. O papel do Flask em uma aplicação web

    Uma aplicação web costuma ser construída em camadas, e cada camada se comunica apenas com as camadas vizinhas:

    • a camada web recebe as requisições HTTP do navegador e devolve a ele páginas HTML. É a camada que o [Flask] nos ajuda a escrever;
    • a camada de negócio contém as regras de negócio da aplicação (por exemplo, “um paciente só pode ter uma consulta futura”). Ela não sabe nada sobre a web: poderia igualmente atender a uma aplicação de linha de comando;
    • a camada de acesso a dados (camada [DAO], de [Data Access Object]) lê e grava no banco de dados. Usaremos o [SQLAlchemy], um ORM ([Object Relational Mapper]) que mapeia as linhas das tabelas para objetos [Python].

    A própria camada web segue o modelo [MVC] ([Model – View – Controller]):

    • o controller (C) é um conjunto de funções [Python], chamadas de actions, cada uma das quais trata um tipo de requisição (por exemplo, [GET /schedule]). Uma action lê os parâmetros da requisição, invoca a camada de negócio e depois escolhe a view a exibir;
    • o modelo (M) é o conjunto de dados que a action transmite à view;
    • a view (V) é um arquivo [Jinja2] (extensão [.html]): uma página HTML que contém expressões [{{ ... }}] e instruções [{% ... %}] ([{% if %}], [{% for %}]...), que a engine [Jinja2] substitui por dados do modelo.

    Uma observação sobre a terminologia, para evitar confusão: a documentação do [Flask] refere-se à função que trata uma requisição como uma “view function” e ao arquivo [Jinja2] como “template”. Este documento usa a terminologia do modelo [MVC], bem como a dos cursos [Spring MVC] e [ASP.NET Core MVC] : a função que trata uma requisição é uma action, o arquivo [Jinja2] que gera a página é uma view, e o termo “template” designa a view comum da qual as outras páginas herdam (Capítulo 4).

    O tratamento de uma requisição segue as etapas numeradas do diagrama:

    • 1: O navegador envia uma requisição HTTP, como [GET /schedule?doctorId=1&day=2026-09-26];
    • 2: O servidor web recebe a requisição e a repassa à aplicação [Flask]. Durante o desenvolvimento, esse servidor é o [Werkzeug], a biblioteca sobre a qual o [Flask] é construído; em produção, será um servidor como o [Waitress] ou o [Gunicorn]. [Werkzeug] compara o caminho solicitado com as rotas da aplicação e seleciona a action responsável por tratar essa requisição: é o roteamento. Antes de chegar à action, a requisição ainda pode passar por funções executadas para todas as requisições ([before_request]), que exploraremos nos capítulos seguintes;
    • 3: A action solicita à camada de negócio os dados de que precisa; se necessário, a camada de negócio aciona a camada [DAO], que consulta o banco de dados [MySQL] por meio de SQL;
    • 4: A action constrói o modelo M da view e instrui a engine [Jinja2] a gerar a página (função [render_template]);
    • 5: A página HTML gerada pela view é a resposta da action, que o [Flask] devolve ao navegador.

    O [Flask] é um dos dois frameworks web mais usados no mundo [Python], junto com o [Django]. Livre e de código aberto, funciona em qualquer lugar em que o [Python] funcione ([Windows], [Linux], [macOS]). É um microframework: seu núcleo é intencionalmente pequeno (roteamento, requisições e respostas, sessões, views [Jinja2]), e todo o resto (validação de formulários, acesso a banco de dados, autenticação etc.) fica a cargo de bibliotecas escolhidas pelo desenvolvedor. Enquanto o [Spring Boot] configura sozinho um conjunto coerente de componentes, [Flask] deixa que o desenvolvedor monte os seus: a aplicação fica mais transparente, e é possível ver tudo o que acontece dentro dela. É justamente isso que o torna uma boa ferramenta de aprendizado: quase nada fica escondido. [Flask] pode criar servidores que devolvem JSON a um cliente [JavaScript] ([Angular], [React], [Flutter]...) assim como aplicações web tradicionais, em que o servidor gera as páginas HTML e o navegador apenas as exibe. Este documento examina esse segundo caso de uso. Dois conceitos de [Python] aparecem em todas as páginas: os decoradores ([@app.get("/")], [@app.before_request]...), que associam uma função a um papel, e a passagem explícita dos objetos de que cada função precisa, ao passo que o [Spring] os injeta automaticamente.

    1.2. Ferramentas utilizadas

    Os exemplos foram escritos e testados com as ferramentas a seguir (sua instalação é descrita no apêndice):

    • [Python] 3.13 (qualquer versão 3.12 ou posterior serve). O instalador do [Python] também fornece a ferramenta [pip], que baixa e instala as bibliotecas, e o módulo [venv], que cria ambientes virtuais (veremos mais adiante o que são);
    • o editor [Visual Studio Code], com a extensão [Python] da Microsoft (que também instala a extensão [Pylance], que analisa o código);
    • um navegador recente ([Chrome], [Firefox], [Edge]);
    • a ferramenta de linha de comando [curl], que exibe as respostas HTTP brutas (ela já vem com o [Windows] 10 e 11);
    • o SGBD [MySQL] (ou [MariaDB]), por exemplo, o do [Laragon] no [Windows], a partir do capítulo sobre acesso a dados e para o estudo de caso.

    Ao contrário do [JDK], que não contém o [Spring], o [Python] vem com uma biblioteca padrão muito completa; mas o [Flask] e as demais bibliotecas do documento não estão incluídos: o [pip] os baixa do repositório [PyPI] ([Python Package Index]) durante a instalação (portanto, é preciso estar conectado à Internet nesse dia).     1.3. Executar o estudo de caso

    Nota do revisor: aconselho o leitor a executar imediatamente o estudo de caso, conforme descrito a seguir. Depois de compreender bem o papel dessa aplicação de consultas, peça à sua IA favorita que modifique a aplicação da seguinte forma: a partir de agora, cada médico poderá:

    • definir seus próprios horários de consulta entre duas datas. Isso permitirá que ajustem a agenda conforme necessário;
    • remover certos horários da agenda em um determinado dia, por exemplo, se estiverem indisponíveis por motivos pessoais;

    A modificação não é simples, pois envolve uma mudança na estrutura do banco de dados. Peça à IA que lhe forneça o novo código da aplicação e o script SQL para criar o novo banco de dados. Para isso, você precisará fornecer a ela o arquivo ZIP com o projeto completo, bem como o script SQL do banco de dados antigo.

Se você tiver dificuldade para entender algo, a solução é sempre a mesma: peça à sua IA favorita que explique o que você não entendeu. Claude, por exemplo, é muito bom nisso. from controllers.pages import pages

# Bootstrap, compartilhado pelos exemplos: a pasta examples/common/bootstrap,

def create_app():
    app = Flask(__name__)
    app.jinja_env.trim_blocks = True
    app.jinja_env.lstrip_blocks = True
    # um blueprint sem rotas, que apenas serve arquivos estáticos: a pasta
    # BOOTSTRAP, sob a URL /bootstrap/...
    app.register_blueprint(Blueprint("bootstrap", __name__, static_folder=BOOTSTRAP,
                                     static_url_path="/bootstrap"))
    app.register_blueprint(pages)
    • Linha 11: o caminho da pasta [common/bootstrap]. [__file__] é o caminho do arquivo em execução ([app.py]); [Path(...).resolve()] o transforma em um caminho absoluto; [.parent] designa a pasta que o contém ([15-layout]), e [.parent.parent] designa a pasta pai ([examples]). O operador [/] de um objeto [Path] acrescenta um elemento ao caminho, usando o separador correto ([\] no [Windows], [/] nos demais). O caminho, portanto, não depende da pasta atual: o exemplo encontra o [Bootstrap] de onde quer que seja iniciado;
    • linhas 20 e 21: um blueprint é um grupo de rotas registrado na aplicação (veja o Exemplo 02). Esse blueprint não tem rotas: serve apenas para publicar a pasta [common/bootstrap] (parâmetro [static_folder]) na URL [/bootstrap] (parâmetro [static_url_path]). Uma página pode então usar a folha de estilo [/bootstrap/css/bootstrap.min.css].

    As demais linhas desse arquivo serão explicadas no Exemplo 15.

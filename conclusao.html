    12. Conclusão

    Este documento apresentou o desenvolvimento de uma aplicação web MVC com o framework [Flask]: uma aplicação cujas páginas HTML são geradas pelo servidor, usando views [Jinja2], sem um framework [JavaScript] no navegador. Ele seguiu passo a passo o curso [Spring MVC], que por sua vez se baseia nos cursos [ASP.NET Core MVC] e [NestJS]: ações e roteamento para views, formulários, internacionalização, segurança e acesso a dados, seguidos de um estudo de caso completo.

    Os mesmos 28 exemplos e a mesma aplicação foram, assim, escritos com quatro frameworks: [TypeScript], [C#], [Java] e [Python]. Os conceitos são os mesmos; só os nomes e os mecanismos mudam. As correspondências entre [Spring MVC] e [Flask]:

    Em comparação com o [Spring MVC], os principais pontos a observar são:

    • O [Flask] é um micro-framework: ele oferece roteamento, requisições e respostas, as views [Jinja2] e o gerenciamento de sessão, e nada além disso. Todo o resto (validação, formulários, segurança, acesso a dados, tradução) fica a cargo de bibliotecas escolhidas pelo desenvolvedor ou escritas por ele. Isso significa mais código a escrever, mas um código transparente: nada acontece “por mágica”, e é possível acompanhar cada objeto desde a sua criação (em [create_app]) até o seu uso;
    • não há contêiner de injeção de dependência: os objetos compartilhados são criados pela factory, armazenados em [app.extensions] e obtidos por meio de [current_app]. Para uma aplicação deste porte, isso é simples e suficiente;
    • Os objetos [request], [g], [session] e [current_app] são proxies que, durante uma requisição, remetem aos objetos dessa requisição. Eles dispensam a passagem da requisição de uma função para outra, mas só podem ser usados durante o processamento de uma requisição (ou dentro de um contexto de aplicação criado manualmente);
    • os decoradores do [Python] têm a mesma finalidade que as anotações do [Java]: rotas, marcações ([@public]) e controles de acesso ([@roles_required]). Mas um decorador é simplesmente uma função que você mesmo pode escrever em poucas linhas;
    • [Python] é uma linguagem de tipagem dinâmica: as anotações de tipo ([list[Doctor]], [Protocol], classes genéricas) documentam o código e orientam o editor, mas não são verificadas em tempo de execução. Ferramentas como o [Pylance] (no [Visual Studio Code]) ou o [mypy] as verificam antes da execução;
    • O [SQLAlchemy] exige a escrita da camada DAO (algumas linhas por consulta), mas suas consultas, construídas com objetos [Python], permanecem próximas do SQL que produzem, e a exibição dos comandos SQL ([SQL_ECHO]) permite verificar o que é enviado ao banco de dados. O carregamento das relações é controlado explicitamente, consulta por consulta;
    • As views [Jinja2] misturam HTML e tags [{{ }}] / [{% %}] : não são páginas HTML válidas como as do [Thymeleaf], mas sua linguagem, semelhante ao [Python], é poderosa (filtros, macros, herança de templates), e o escape automático protege contra injeção de HTML.

    O estudo de caso mostra que uma aplicação HTML clássica, sem o [JavaScript] como elemento essencial, continua sendo uma solução simples e robusta: cada página é uma URL, o botão “Voltar” do navegador funciona e o servidor controla tudo. O uso limitado de [JavaScript] (janelas de confirmação) melhora a experiência do usuário sem ser necessário para o funcionamento da aplicação.

    Para saber mais, você pode consultar a documentação do [Flask] (flask.palletsprojects.com), [Jinja2] (jinja.palletsprojects.com), [Werkzeug] (werkzeug.palletsprojects.com), [WTForms] (wtforms.readthedocs.io) e [Flask-WTF] (flask-wtf.readthedocs.io), do [SQLAlchemy] (docs.sqlalchemy.org), do [Pydantic] (docs.pydantic.dev) e comparar esta aplicação com suas equivalentes em [Spring MVC], [ASP.NET Core MVC] e [NestJS].
